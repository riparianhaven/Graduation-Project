## 内核性能优化（1.5 s → 0.15 s／帧，逐位不变）

**任务**：分析并优化仿真代码的速度，保持精度/边界/功能不变；说明瓶颈、措施、验证方法。

**定位**：瓶颈不是浮点，是 numpy 的**每次调用开销**。`simulate_seq` 每步 60–80 次
ufunc（3 元数组上一次 ≈0.4 μs），47124 步 × m=3 就是 1.45 s，真正的浮点只占几纳秒。
实测支撑：3 路阵列 1.448 s vs 3 次单路 0.40 s（阵列在小 m 上反而慢 3.6×）；
m 从 16 涨到 180 总耗时只涨 1.7 倍（每次调用摊到更多路上）。

**改动（只改求值方式，不改运算顺序）**：
- `KERNEL_SRC` 重写：m ≤ 32 走**微内核**（驱动表按列预算成 Python float 列表 +
  纯标量 RK4）；m > 32 仍走向量路径（`np.abs(x, out=ab)` 复用缓冲、`h12/h16` 外提）。
- `estimate_amp`：`np.repeat` 68 MB → `np.broadcast_to`（0 拷贝）。
- 阈值 32 来自实测交叉点 ≈40（m=16 快 2.1×、m=32 快 1.16×、m=64 慢 1.5×）。

**三条不能碰的红线（实测）**：
1. `x**3` 不能换 `x*x*x`：200000 个样本里 **51845 个位模式不同**（最大 2.8e-14）。
   而 CPython `float.__pow__` 与 `np.power` **逐位相同**（0/20000）。
2. `np.cos` 与 `math.cos` 在 float64 上**逐位相同**，且**与数组长度/形状无关**
   （20000 点 0 差异）→ 这是"把驱动项搬出循环"唯一的合法性依据。
3. `p.std(axis=0)` 的归约顺序跟内存布局有关：`.T` 出来的 **F 序比 C 序差 1 ulp**。
   微内核必须 `np.ascontiguousarray(p)`，否则"逐位相同"承诺就没了。

**没做的事及理由**：numba/cython 未安装；16 个 R 的多进程（每个任务 47 ms，
Windows spawn 约 1.5 s/进程，串行 0.75 s 反而更快）；多线程（纯 float 循环持 GIL）；
缩短瞬态（改论文口径）。并行轴本来就是**通道维**（`pstd_batch` 按 K×3 拼列）。

**验证**：新增 `tests/test_kernel_golden.py`（13 项）——改动前用旧内核把 11 个算例的
`p/ pstd / mx / trace.X` 冻结成 `tests/golden/kernel_ref.json`（含 sha256），改动后
断言**逐位相等**（不用容差：混沌态 1 ulp 会被指数放大）。覆盖 m=1/2/3/32/45/180、
trace、`i≥n` 的零阶保持、burn_frac=0.3、R=7.3/3.7。另加
`test_two_paths_agree_at_the_switch_boundary`（m=32 微内核 vs m=33 阵列，前 32 列全等）。

用户一句「同步修改 README-ESP32-固件实现.md」，做的是**规格级对齐**（不只是改数字）：
