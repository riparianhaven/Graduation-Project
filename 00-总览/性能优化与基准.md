# 性能优化与基准：把一帧判决从 1.5 s 压到 0.15 s

> 目标：**不改数值、不改边界行为、不改功能**，只改"怎么算"。
> 结论：默认链路（已知 R 判一帧）**10×**、盲测扫 R **3.9×**、两级细扫 **2.7×**；
> 11 个算例的 Poincaré 点 sha256 与优化前**逐位相同**。
>
> 复现：`py tools/bench_speed.py`（速度）＋ `py -m pytest tests/test_kernel_golden.py -q`（一致性）。

## 一、先定位：慢的不是浮点，是 numpy 的"每次调用"

一帧 94.2 s、$f_s=500$ Hz 就是 47100 个样本，内核要积分 47124 步。原来的
`simulate_seq` 在**每一步**里做这些事：

```python
f1 = lam * np.cos(tau + beta) + s0            # 4 次 ufunc
fh = lam * np.cos(tau + h1/2 + beta) + 0.5*(s0+s1)   # 6 次
f4 = lam * np.cos(tau + h1 + beta) + s1       # 4 次
k1y = -K*y + x**3 - x**5 + f1                 # 6 次   × 4 次 RK4 级
x2, y2 = x + h1/2*k1x, y + h1/2*k1y           # 4 次   × 6 次中间步
x = x + h1/6*(k1x + 2*k2x + 2*k3x + k4x)      # 7 次   × 2 个分量
```

数下来**每步 60–80 次 numpy 调用**。三通道时数组只有 3 个元素，
每次调用的固定开销（分派、检查、创建返回数组）约 $0.4\ \mu s$，
实测 $1.448\ \text{s}/47124 = 30.7\ \mu s$／步 ÷ 74 ≈ $0.41\ \mu s$／次——
**浮点运算本身只占其中几纳秒**。换句话说：

> 慢的根因是"用 numpy 做标量运算"。3 元数组上，numpy 的调用开销是
> 它算的那点浮点的上千倍。

三条实测支撑这个判断：

| 观察 | 数据 | 含义 |
|---|---|---|
| 3 路阵列 vs 3 次单路（老标量快路径） | 1.448 s vs 3×0.134 s = 0.40 s | 通道少时阵列路径反而**慢 3.6 倍** |
| 通道数 16 → 180 的总耗时 | 1.52 s → 2.59 s（只涨 1.7 倍） | 每步调用次数不变，摊到 180 路上就便宜了 |
| 微内核单通道单步 | $0.89\ \mu s$／步（约 45 次 Python float 运算） | 纯标量算术比 numpy 小数组快**一个量级** |

## 二、优化措施

### 2.1 把驱动项搬出循环（预算表）

`λcos(τ+β)+s(τ)` 只依赖步号，与状态 $(x,y)$ 无关，却放在循环里算了 47124 遍。
现在按列在循环外一次算成 Python float 列表。

**合法性依据（实测，不是推断）**：`np.cos` 在 float64 上对同一输入
**逐位等于** `math.cos`，且**与数组长度/形状无关**——20000 个点上逐位比对
0 处不同，`(steps,3)` 的二维调用与逐步的 3 元数组调用也完全相同。
所以搬出循环改的只是"什么时候算"，不是"算出了什么"。

### 2.2 小通道数走微内核（本次最大收益）

$m \le 32$ 时不再用数组，改成**逐通道的纯 Python float** 循环：驱动项从
预算表里取，RK4 的四级算术全是 `float`。同一套公式、同样的运算顺序。

| 通道数 | 阵列路径 | 微内核 | 比值 |
|---|---|---|---|
| 1 | 0.134 s | 0.042 s | **3.2×** |
| 3（三相位阵列，GUI 默认） | 1.448 s | 0.126 s | **11.5×** |
| 16 | 1.519 s | 0.711 s | 2.1× |
| 32 | 1.690 s | 1.458 s | 1.16× |
| 64 | 1.863 s | 2.732 s | 0.68× |
| 180（估幅网格） | 2.591 s | 7.786 s | 0.34× |

交叉点在 40 路附近，阈值取 **32**（偏保守）。超过 32 路时阵列的
"一次调用摊 180 路"仍然无可替代，所以两条路径都保留——但**必须逐位一致**，
`tests/test_kernel_golden.py::test_two_paths_agree_at_the_switch_boundary`
在 m=32/33 的边界上钉死这件事。

### 2.3 去掉循环内的重复分配

| 原来 | 现在 | 省掉 |
|---|---|---|
| `np.maximum(mx, np.abs(x), out=mx)` 每步新建 `abs` 数组 | `np.abs(x, out=ab)` 复用缓冲 | 4.7 万次临时数组／帧 |
| `np.repeat(x.reshape(-1,1), 180, axis=1)` | `np.broadcast_to(...)` | 一次 **68 MB** 拷贝 |
| 每步重算 `h1/2`、`h1/6`、`i*h1` | 循环外算一次；步进时间轴用 `np.arange(steps)*h1`（与 `i*h1` 逐位相同） | 每步 3 次标量运算 |

### 2.4 一个必须踩到的坑：`std` 的归约顺序跟内存布局有关

微内核按通道收集点，最自然的写法是 `np.array([...]).T`——那是 **F 序**。
`p.std(axis=0)` 在 F 序上会走另一条归约路径，结果差 **1 ulp**（实测
`pstd=2.4e−3` 这种量级上末位差 1，肉眼永远看不见，但它足以让哈希比对失败）。数值上无所谓，但"逐位相同"的承诺就没了。
统一 `np.ascontiguousarray(p)` 后与阵列路径完全一致。

### 2.5 明确**没有**做的事

| 想做的优化 | 为什么不做 |
|---|---|
| `x*x*x` 代替 `x**3`、`x*x*x*x*x` 代替 `x**5` | 实测 200000 个样本里 **51845 个位模式不同**（最大差 2.8e−14）。混沌态会指数放大，等于换了题 |
| `x**3` 改 `np.multiply` 两连乘 | 同上：CPython 的 `float.__pow__` 与 `np.power` 逐位一致（实测 0/20000 不同），但与连乘不一致 |
| numba / cython 重写循环 | 环境里没有（`numa`/`cython` 均未安装），且会给交付物加编译依赖 |
| 多进程并行 `scan_R` 的 16 个 R | 每个任务 47 ms，Windows spawn 一个进程约 1.5 s（要重新 import numpy）。16 个任务串行 0.75 s，**并行反而更慢** |
| 多线程 | 纯 Python float 循环全程持 GIL；numpy 只在大数组上放 GIL，这里数组只有 3 个元素 |
| 减少积分步数 / 缩短瞬态 | 直接改数值。`steps` 由 `n_cycles` 与 $h_1$ 决定，是论文口径 |

**并行这件事本项目早就做了**，并行轴是**通道维**而不是时间维：RK4 沿时间是
严格串行的，但 $m$ 路振子（三相位阵列、估幅的 4×45 网格、批量试验）互相
独立，一次数组调用算完所有路——`pstd_batch` 按「K 次试验 × 3 相位」拼列，
$m=90$ 时 21 ms／路 vs 逐路 140 ms／路，快 7 倍。这次只是把"小 $m$ 时并行
不划算"这件事也按实测分了档。

## 三、一致性怎么验证

### 3.1 黄金样本：优化**前**冻结，优化**后**比对

`tests/golden/kernel_ref.json` 是改动之前用当时的内核跑出来的，存了每个算例的
`pstd`、`mx`、Poincaré 点矩阵 `p` 的 **sha256**、以及 trace 的 `X` 的 sha256。

```bash
.venv\Scripts\python.exe -m pytest tests/test_kernel_golden.py -q
# 13 passed
```

**为什么用哈希而不是容差**：混沌系统里 1 ulp 的差异会被指数放大，用
`np.allclose` 只能证明"量级没变"，证明不了"数值没动"。哈希相等才是真的没动。

覆盖的形状（`tools/kernel_cases.py`，测试/基准/重冻结共用一份）：

| 算例 | 覆盖的东西 |
|---|---|
| `idle-lam-072-076` | 全零序列（内驱 0.72 混沌 / 0.76 周期）、m=2 |
| `scalar-lock` | m=1、20000 点、锁定态 |
| `three-phase` / `-trace` | GUI 默认三相位阵列；trace 的 `T/X/Y` 形状与内容 |
| `m32-broadcast` | 单列广播到 32 路（微内核） |
| `m45-vector` | 45 路（阵列路径） |
| `short-sig-long-int` | 序列只有 5000 点、却积分 300 个周期 → `i ≥ n` 的零阶保持分支 |
| `burn-0.3` | 非默认瞬态比例 |
| `R-7.3` / `R-3.7` | 变尺度（不同 $h_1$，截面落点不同） |
| `amp-grid` | 4 相位 × 45 个 λ 的估幅网格（180 列） |

### 3.2 两条路径的边界

`test_two_paths_agree_at_the_switch_boundary` 把同一列复制到 32 路（微内核）
与 33 路（阵列）上，断言前 32 路的 `pstd`/`mx`/`p` **完全相等**。这是"换求值
方式不改数值"的核心契约。

### 3.3 上游功能测试照旧

`pytest tests -q` → **111 passed**（原有 98 项 + 新增 13 项黄金样本）。
其中 `test_kernel_contract.py` 的 22 项继续保证"一个内核、五个 notebook
正文逐字一致"。

## 四、速度提升（本机实测，Python 3.13.9 / numpy 2.4.6）

| 场景 | 优化前 | 现在 | 加速 |
|---|---|---|---|
| 内核 m=1（单振子，47124 步） | 0.133 s | **0.041 s** | 3.2× |
| 内核 m=3（三相位阵列） | 1.448 s | **0.126 s** | 11.5× |
| 内核 m=45（阵列路径） | 1.751 s | 1.664 s | 1.1× |
| 内核 m=180（估幅网格） | 2.591 s | 2.526 s | 1.0× |
| **`analyze(known)` 一帧判决** | 1.513 s | **0.148 s** | **10.2×** |
| `analyze(auto)` 盲测扫 R | 3.631 s | **0.920 s** | 3.9× |
| `scan_R` 两级细扫（16 次单振子） | 2.047 s | **0.747 s** | 2.7× |
| `estimate_amp` λ\* 差分 | 2.650 s | 2.604 s | 1.0× |
| `framework_demo`（200×2 次） | 0.045 s | 0.045 s | — |
| `make_frame` 一帧 | 1 ms | 1 ms | — |

**为什么估幅（m=180）没变快**：它本来就走阵列路径，每步 53.6 µs 摊到 180 路
只剩 0.30 µs／路／步，numpy 的调用开销早已摊薄；剩下的时间是真的在算
$180\times47124$ 条轨迹。要再快只能上 numba 或换硬件，不属于本次范围。

**界面上的变化**：接收端「已知 R」判一帧 1.4 s → **约 0.15 s**（含估幅
4 s → 约 2.8 s），波形、频谱、相图、时序条的刷新不再有明显延迟。

## 五、边界行为没动

| 行为 | 状态 |
|---|---|
| 发散（`|x|=inf/nan`）检测：每 256 步查一次，返回 `pstd=全 NaN`、`p` 空 | 不变 |
| `p` 只取截面点的**后一半**（丢瞬态）+ `np.std(axis=0)` | 不变（含归约顺序） |
| `i ≥ n` 时样本项取 0（序列短于积分步数） | 不变 |
| 末点 `s1 = s0`（零阶保持的边界） | 不变 |
| Poincaré 取精确 $\tau=2\pi k$ 的线性插值（`frac` 用补角） | 不变 |
| `trace=True` 时 `T/X/Y` 的形状（m=1 → `(steps,1)`，m>1 → `(steps,m)`） | 不变 |
| 发散返回时的 `mx` | 由"部分累加值"改为"全 NaN"（只在发散这条错误路径上可见，无调用方依赖） |

## 七、一句话小结

> 这个仿真的时间几乎全花在"用 numpy 做标量运算"的调用开销上。
> 把驱动项搬出循环、把 $m\le32$ 的通道换成纯 Python float，就拿到了
> 一个数量级；真正的浮点运算顺序一个字都没改，所以网格、阈值、pstd
> 与优化前逐位相同。
